# Subscriber post access: investigation and prior art

The product goal is browsing media from memberships the signed-in user **pays for**. Creator-token access is not a substitute.

## What is established

- The app successfully retrieves membership identity data via Patreon OAuth (`identity.memberships`), as shown by the connected user's screenshot.
- The user's captured posts error was **HTTP 400 `ParameterInvalidOnType`**, with detail `Invalid parameter for 'include' on type post: ['attachments', 'media']`. This was a request validation error, **not evidence of access denial**. The app no longer sends that `include`; it requests documented Post v2 fields and displays upstream error details in the UI. Live access with this corrected request still needs to be tested with the user's session.
- Patreon's published docs say `GET /api/oauth2/v2/campaigns/{campaign_id}/posts` requires `campaigns.posts`; our default OAuth scopes are only `identity identity[email] identity.memberships`. The docs say `GET /api/oauth2/v2/campaigns` returns campaigns **owned** by the authorized user. They do not establish that granting `campaigns.posts` to a paying subscriber gives access to arbitrary other creators' posts. This remains unverified and must not be promised.
- The documented next-page cursor is `meta.pagination.cursors.next`; the server now reads it (with a fallback for `links.next`).
- The publicly accessible campaign page is a Next.js-rendered page and contains page data and public media URLs in its HTML. That alone says nothing about subscriber entitlement.
- **Subscriber browser observation:** a signed-in Patreon tab returned nonempty `/api/posts` responses for the subscribed Bloom County campaign. Feed entries had `current_user_can_view: true`, `post_type: image_file`, title, date, and image URLs. A fuller posts response also had `post_file`, `content_json_string`, `relationships.images` and `relationships.media`, while pagination metadata was not included in the supplied excerpt. This confirms website post discovery for this user's session; it does not prove full-resolution media download, video playback, or availability across every membership.
- `is_preview_blurred: true` and `upgrade_url` appeared alongside `current_user_can_view: true`; these flags must **not** be used alone to infer entitlement or to assume a displayed URL is an unblurred original. `is_paid: false` denotes a different post billing property, not proof a post is public. Signed CDN URLs expire; never persist them as a durable archive or include them in diagnostic logs.
- Further signed-in samples showed that a post with a PDF attachment can have `post_type: text_only`, `attachments_preview_metadata` (filename/MIME/size), and `relationships.attachments_media.data` containing only a media **ID**. An extension must resolve `included` media records or a post detail response before offering an actual file download; neither a filename nor a relationship ID is a download URL. `content_json_string` may provide the post description. Do not determine media type solely from `post_type`.
- The first supplied `links.next` and `meta.pagination.cursors.next` belonged to `/api/posts/{id}/conversations` (comment threads). **A separate post-feed response now confirms `links.next`** on the signed-in website endpoint `/api/campaigns/{campaign_id}/posts`. Its URL carries the next `page[cursor]`, `page[count]`, filters, fieldsets, and sort. It is distinct from the documented OAuth v2 `/api/oauth2/v2/campaigns/{campaign_id}/posts`, which returned zero items for the subscriber token. A browser-session client should follow/validate the feed's `links.next` on `www.patreon.com`, cap pages, de-duplicate IDs, and avoid logging or persisting cursor URLs; do not reuse comment cursors. The sampled feed sorts by `-recency_weighted_engagement`, not strictly by date, so the gallery must sort retrieved posts itself and must not assume the first page is chronologically newest. The attachment sample still does not establish how videos are represented or whether the original PDF URL is available.

Source: [Patreon API documentation](https://docs.patreon.com/) — *APIv2: OAuth*, *GET /api/oauth2/v2/campaigns/{campaign_id}/posts*, *Post v2*, and *Pagination Changes* (checked during this investigation).

## Relevant public prior art (source inspected; not run)

- [patrickkfkan/patreon-dl](https://github.com/patrickkfkan/patreon-dl) documents patron-only access via a user's existing browser cookie (README), and constructs requests to Patreon's **website** `/api/posts` rather than the documented OAuth v2 campaign-post endpoint ([URLHelper.ts](https://github.com/patrickkfkan/patreon-dl/blob/master/src/utils/URLHelper.ts)). It filters posts by `campaign_id`, can use `accessible_by_user_id`, and handles `include` relationships such as `attachments_media` and `images`. Its cookie-based CLI approach proves an architectural pattern, not that any current endpoint is stable, authorized under Patreon terms, or suitable for storing cookies in this app. Do **not** copy session cookies into our backend merely to mimic it.
- [sneat/patreon-downloader](https://github.com/sneat/patreon-downloader) is a Manifest V3 browser extension. Its [content script](https://github.com/sneat/patreon-downloader/blob/main/src/contentScript.js) calls a same-origin website `/api/posts/{id}` with `credentials: "include"`, falling back to post data already serialized into the rendered Next.js page. This supports testing a small extension in the user's signed-in browser. It also demonstrates fragility: the source handles both legacy `__NEXT_DATA__` and newer `self.__next_f` bootstrap formats. Inspect permissions and privacy before adopting any extension design.
- [AlexCSDev/PatreonDownloader](https://github.com/AlexCSDev/PatreonDownloader) and [banjophil/patreon-downloader](https://github.com/banjophil/patreon-downloader) separately show cookie-driven download and DOM-interaction extension approaches; the latter README warns slideshows require driving the site's UI and that its extension is not actively maintained.

These projects are **research leads, not dependencies or endorsements**. No third-party code was executed and no paid content or credentials were collected. The website `/api/posts` endpoint appears to be first-party/undocumented, distinct from OAuth v2: schema and authorization behavior may change. Respect Patreon terms, creator rights, account entitlements, and DRM; do not attempt to bypass access controls.

## Browser-session architecture candidates

1. **Retry the corrected official OAuth API request**. If it now returns a scope error, request the documented `campaigns.posts` scope and verify whether it actually authorizes a subscriber for a *different creator's* campaign. Never infer that from creator-token behavior. A list of post titles without media still would not satisfy the gallery goal.
2. **User-installed Chrome/Edge extension reading the logged-in site**. A content script can observe only Patreon pages the user visits and extract rendered post cards/links/media that the site already delivers to that account. A reusable WebExtension architecture might support Firefox later. Avoid copying cookies, passwords, or bearer tokens into this app. Pagination and completeness need a small proof-of-concept with a real paid membership.
3. **Browser automation using a user-controlled Chrome profile**. Possible as a local-only alternative, but brittle against site changes and carries greater session/profile security risk.
4. **Reverse-engineering first-party network endpoints**. Potentially possible because the browser loads paid pages somehow; requests may involve CSRF tokens, cookies, signed expiring CDN URLs, internal protocols, and changing schemas. Do not implement cookie export, auth bypass, unattended scraping, or redistribution without reviewing Patreon terms and the creator's rights. This option is less stable and harder to maintain than observing rendered content in the user's own tab.

**The user ran the extension in a signed-in Chrome session.** It showed 11 viewable posts over two pages from the initially observed `/api/campaigns/{id}/posts` feed, including previews. That short result was not the entire archive: after switching to `/api/posts?filter[campaign_id]=…&sort=-published_at&page[count]=20`, the user reported that browsing worked much better, including additional images. The next issue was reversed temporal navigation and the lack of an oldest-unread starting point. The extension scans remaining pages for **Media viewer · oldest unread**, then navigates media chronologically (← older, → newer) with jump controls. Separate **Load oldest post** and **Load oldest unread post** actions scan the archive and show all viewable post cards (including text posts) oldest-first, focusing the chosen card without marking it opened. Exact scan behavior and completeness beyond the 100-page safety limit still need checking in the user's signed-in session. The developer environment does not have that session. After an extension update, the user reported that no feeds were detected. A signed-out browser navigation to the same creator's `/c/<vanity>/posts` route redirected to `/cw/<vanity>/posts`, which the extension had not recognized; previously-open Patreon tabs may also lose their content-script listener on extension reload. The updated extension recognizes `/cw/`, can resolve that page's vanity through the same-origin campaign lookup, and reinjects only packaged scripts into an eligible `www.patreon.com` tab if messaging fails. This recovery remains to be verified in the user's signed-in tab.

## Decision gate

The official OAuth v2 campaign-post request returned `200` with `items: []` for this subscriber membership, while the signed-in website endpoint returned accessible post records. The Chrome Manifest V3 prototype in `extension/` now discovers a campaign from the signed-in tab, requests the chronological `/api/posts` archive instead of the short engagement-weighted campaign feed, follows validated same-campaign `links.next` up to 100 pages (user-paced while browsing or sequentially after a user starts a gallery scan), filters `current_user_can_view === true`, and offers a full-window media viewer with chronological navigation, original images when safely available, and preview fallbacks. It does not read/export cookies. The current prototype adds guarded per-asset Chrome downloads, direct-video playback, click-to-load embeds for validated Vimeo links (with a restricted iframe policy), a YouTube-thumbnail/watch-link fallback because its player returns error 153 in Chrome extension pages, preview/link fallbacks for unsupported videos, type-specific file icons with filenames from Patreon metadata, separate Open/Download actions on cards and file rows, and explicitly confirmed batch jobs. Browser-supported files open in a tab; other files require a user-initiated download followed by a separate **Open downloaded file** click (or Chrome Downloads if the browser blocks launching them). A validated YouTube watch-URL list can be exported for the separately installed `yt-dlp` tool, including multiple links in a viewable text post's body (not just its `embed` field). Plain text-post covers open their original Patreon posts. The extension does not download YouTube streams or export Patreon cookies/signed media URLs. A file attachment is offered only when its relationship ID resolves to an included media record with a safe `download_url`; thumbnails and media IDs are never treated as files. Public prior art warns that some video `included.download_url` values return 404, so video downloads use `post_file.download_url` (or a direct file URL) rather than media previews. **Video, file, and download behavior still require testing with the user's paid session; queued Chrome downloads can still fail from expired media URLs.** Keep the prototype local and user-paced; do not attempt DRM bypass, redistribute posts, or persist signed CDN URLs. Consider Firefox after Chrome is verified.
